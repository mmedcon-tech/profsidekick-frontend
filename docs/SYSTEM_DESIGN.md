# ProfSidekick Frontend — System Design Document

Scope: `profsidekick-frontend` repo only (`D:\code\mmedcon\profsidekick\profsidekick-frontend-main`), branch `version2`, indexed in GitNexus as `profsidekick-frontend` (343 files, 2668 symbols, 6198 relationships). Investigation performed read-only via the GitNexus knowledge graph plus direct source reads; no code was modified. Cross-repo behavior (backend-main / `profsidekick-api`) is explicitly out of scope and marked `[CROSS-REPO — see backend SDD]` wherever the frontend hands off to it.

---

## 1. Executive Summary

ProfSidekick's frontend is a Next.js 15 / React 19 App Router application that serves three actor surfaces (`/admin`, `/publisher`, `/subscriber`) plus a voice/3D-avatar "run" experience built on the OpenAI Realtime API, Three.js/`@react-three/fiber`, and a feature-flagged (currently disabled) HeyGen video-avatar integration. Almost every route is a thin Next.js Route Handler that proxies to a FastAPI backend (`src/lib/proxyAuth.ts`, `src/lib/config.ts`) — the frontend holds very little independent business logic. The codebase shows clear signs of an in-place architecture migration: a first-generation "professor persona" system (`src/hooks/useProfessorPersona.ts`, `src/components/professor/*`, `src/constants/teachingAssistant.ts`, `src/constants/examinerPrompt.ts`, `src/constants/simpleHandoff.ts`) was superseded by a second-generation "Avatar Template → Publisher Avatar → Avatar Configuration" system (`src/lib/avatarApi.ts`, `src/types/avatar.ts`) but was never deleted — GitNexus confirms zero live references into the entire old system. The single biggest architectural risk found is **not** hardcoded pricing (none was found — see §5) but a **broken session-completion write path**: the frontend computes rich end-of-session data (duration, feedback, rubric outcome) client-side and then silently discards it instead of sending it to the backend's `/stop` endpoint, meaning session-run completion, as authored today, never reaches the backend through the code paths GitNexus and manual tracing could find. A secondary risk is a stale `README.md` describing a completely different (pre-auth, pre-multi-tenant) MVP architecture, which is actively misleading for onboarding.

### 2.2 Divergence from the conceptual brief
The brief describes one "AI persona" concept; the frontend actually contains **two generations of it**, only one of which is wired up. The brief describes "session" as a single concept; the frontend has three overlapping session-shaped types (`ClassSession`, `SessionDetails`, `SessionRunDetails`) with inconsistent field casing (`session_duration_minutes` vs `sessionDurationMinutes`-style) and an explicit "legacy" label attached to the type that is actually in production use.

## 3. High-Level Architecture

- **Framework**: Next.js 15 (App Router) + React 19 + TypeScript, Tailwind CSS, Radix UI primitives (`package.json`).
- **3D/Avatar rendering**: `three` + `@react-three/fiber` + `@react-three/drei` for GLB avatars (`src/components/avatar/GlbAvatar.tsx`, `GlbAvatarPreview.tsx`, `TeachingSessionAvatar.tsx`); HeyGen streaming avatar via `@heygen/streaming-avatar`, gated behind `NEXT_PUBLIC_HEYGEN_ENABLED` and proxied through `src/app/api/heygen/token/route.ts` (server-side API key, `HEYGEN_API_KEY`) — confirmed disabled-by-default in `src/lib/heygenConfig.ts:4-9`.
- **Realtime voice AI**: `openai` SDK + WebRTC, ephemeral-token pattern — frontend never holds an OpenAI API key; it fetches a short-lived token from the backend (`src/lib/sessionService.ts:17-65`, backend route `/api/session/ephemeral`).
- **Backend integration pattern**: virtually every domain read/write is a **BFF proxy** — a Next.js Route Handler under `src/app/api/**` that forwards the caller's Bearer token to `NEXT_PUBLIC_BACKEND_URL` (`src/lib/config.ts`, `src/lib/proxyAuth.ts`). Two parallel client conventions exist in `src/lib/avatarApi.ts`: `req()` (calls the backend directly with a browser-stored token) and `bffReq()` (calls the frontend's own `/api/**` proxy, which itself calls the backend) — both are live, used for different endpoint families, which is itself a minor consistency debt item (see §6).
- **Payments/third-party billing**: no Wix SDK, Wix API call, or the string "wix" appears anywhere in `src/` (verified by full-repo text search); billing is entirely a first-party **credit ledger** exposed by the backend (`/api/billing/balance`, `/api/billing/usage`, `/api/billing/redeem`, `/api/billing/add-credits` — `src/lib/config.ts:44-49`). See §5 for full analysis.
- **Auth**: JWT stored in `localStorage` (`src/lib/authSession.ts`, `src/contexts/AuthContext.tsx`), proactive refresh + 401-retry-once pattern in `src/lib/api.ts`. Route protection is client-side only (`src/components/auth/ProtectedRoute.tsx:23-28` — redirects if `!isAuthenticated`; no server-side Next.js middleware file exists in the repo, and no role check is performed here — role-based authorization is `[ASSUMPTION: enforced backend-side per-route]`, not verifiable from this repo).

## 4. Key Flows

### 4.1 Persona / avatar customization flow (publisher-side)

1. Publisher picks a published `AvatarTemplate` → names the avatar → sets `TeachingPreferences` in a 3-step wizard: `src/app/publisher/avatars/new/page.tsx` (`CreateAvatarPage`, `handleCreate` lines 147-165). Preferences (`pace`, `questioning_style`, `formality_level`, `depth_level`, `encouragement_level`, `language_level`) are sent via `avatarApi.create()` → `bffReq('/api/publisher/avatars', 'POST', …)` (`src/lib/avatarApi.ts:257-258`) → persisted server-side.
2. A **"Post-Session Check" toggle** on the same wizard screen (`src/app/publisher/avatars/new/page.tsx:329-346`) is explicitly labeled in the UI copy: *"Post-session check configuration is stored locally and will be activated in a future release"* and the surrounding code comment confirms `// Post-session check: UI-only, not sent to backend yet` (line 122). This is a genuine, self-documented client-only stub — not wired to any API call.
3. Voice/language/difficulty and the **3D model binding** are set on a separate screen, `src/app/publisher/avatars/[id]/configure/page.tsx`: `selectModel()` (lines 81-90) writes `renderType: '3d'` and `glbLibraryId` into `form.additional_settings`, an untyped bag (`AvatarConfigurationCreate.additional_settings: Record<string, unknown>`, `src/types/avatar.ts:148`). Saved via `configApi.upsert()` → PUT/POST `/api/publisher/avatars/{id}/configuration` (`src/lib/avatarApi.ts:297-324`), a `bffReq` call, i.e. persisted server-side, not local-only.
4. A "refine prompt" capability exists (`src/hooks/useProfessorPersona.ts:96-127`, backed by `/api/professor/persona/refine` → `proxyToBackend` in `src/app/api/professor/persona/refine/route.ts`), but this entire hook and its three UI components (`AvatarPicker.tsx`, `PreferencesForm.tsx`, `RefinedPromptEditor.tsx`, all in `src/components/professor/`) have **zero incoming references anywhere in the app** — confirmed via `context()` (each returns `"incoming": {}`) and `impact(direction: upstream)` (`impactedCount: 0`), and via `route_map()` showing `useProfessorPersona.ts` as the *only* consumer of `/api/professor/persona` and `/api/professor/persona/refine`. There is no reachable UI path to this refine flow today.
5. Per-session behavior (hint policy, rubric, extra instructions) is set separately from the avatar-level persona, in `src/components/sessions/AISettings.tsx` (`handleSubmit`, lines 233-298), POSTed to `/api/sessions/{sessionId}/update`. The comment at lines 136-138 states the backend's `prompt_builder.py` always assembles the core exam prompt server-side and ignores any client-sent "core" field — i.e., the actual instruction-assembly logic is confirmed to live in the backend, not here. `[CROSS-REPO — see backend SDD]` for `prompt_builder.py` itself.

**Net finding**: the *live* persona/avatar-binding flow is fully backend-persisted (no localStorage-only persistence for anything that visibly affects session behavior), except the one explicitly-labeled "Post-Session Check" stub (§6).

### 4.1a Voice provider selection — a half-built dual pipeline (updated finding, added after initial pass)

The backend implements a genuine dual voice-provider architecture, not just an OpenAI-only one: `AvatarConfiguration.tts_provider` (`[CROSS-REPO]` backend `app/database/models/avatars.py:71-94`), `voice_resolution_service.resolve_session_voice()` (`[CROSS-REPO]` `app/services/voice_resolution_service.py:46-96`, resolves subscriber-preference override → publisher default, backward-compat-inferring `"elevenlabs"` for any voice string that isn't a known OpenAI voice name via `infer_provider_from_voice`), and `PricingConfig` rates for both `tts_openai` and `tts_elevenlabs`. The ephemeral-token endpoint carries an explicit code comment describing the intended split: *"OpenAI Realtime's own audio.output.voice must be an OpenAI voice name; ElevenLabs voice ids don't apply here since the frontend runs Realtime in text-only mode and synthesises separately"* (`[CROSS-REPO]` `app/api/sessions/api.py:1521-1526`), and the ephemeral response surfaces `voice_provider`/`voice_id`/`voice_dialect`/`voice_source` fields for exactly this purpose (`sessions/api.py:1682-1689`).

**This repo never implements its half of that design:**
- The only UI surface where a publisher sets an avatar's session voice — `src/app/publisher/avatars/[id]/configure/page.tsx:17,122-127` (`const VOICES = ['alloy','ash','ballad','coral','echo','sage','shimmer','verse']`, rendered as the picker under the label "The voice your avatar uses during sessions") — offers **only the 8 native OpenAI Realtime voice names**. There is no ElevenLabs option, no free-text voice-id field, nothing. Default fallback when unset is `'alloy'`. A `tts_provider="elevenlabs"` avatar configuration can only exist today via a path this repo's live UI does not expose.
- `src/lib/elevenLabsSpeech.ts` / `synthesizeWithElevenLabs` (`src/app/api/tts/elevenlabs/route.ts:50-115`) is real, working ElevenLabs synthesis code — but its only caller is that same route's own `POST` handler, part of a standalone voice-**preview/audition** feature (`useSpeechPreview.ts`, the `PickElevenLabsVoiceId` process in the graph), disconnected from the live learning-session runtime entirely.
- Neither live session component reads the provider fields the backend sends: text search for `voice_provider|voice_source|elevenlabs|text-only|modalities` across `TeachingInterface.tsx`, `LearningInterface.tsx`, `sessionService.ts`, and `avatarConfig.ts` returns **zero matches** for the first four terms in all four files. `TeachingInterface.tsx:1130-1134` unconditionally sends `modalities: ["text", "audio"]` on every `response.create` call — i.e., the frontend always asks OpenAI to speak natively, regardless of which provider the backend resolved.

**Failure mode**: if an avatar is ever resolved to `provider="elevenlabs"`, the backend still charges the `tts_elevenlabs` rate and returns the correct `voice_id`, but the learner hears OpenAI's own (default/last-configured) voice instead — a silent mismatch with no error thrown, not a crash. This is exactly the kind of bug that survives casual testing because nothing fails loudly.

**Downstream architectural consequence — interruption handling**: `src/lib/realtimeInterrupt.ts:interruptActiveResponse` (lines 21-42) implements all barge-in exclusively through OpenAI Realtime's own WebRTC data-channel messages (`response.cancel`, `output_audio_buffer.clear`, `conversation.item.truncate`). This only works because OpenAI is the one producing and streaming the audio. If the ElevenLabs half of the design were completed as the backend's own comment specifies — OpenAI running text-only, with audio synthesized and played back separately — this interrupt function would not stop that separately-played audio at all. A second, independent barge-in path (detect learner speech → stop/cancel local ElevenLabs playback) would need to be designed and built; nothing resembling it exists in the traced code today. The same shape of gap likely extends to the (currently feature-flagged-off) HeyGen integration, which per earlier tracing receives OpenAI's realtime text/audio feed directly — an ElevenLabs-primary pipeline would require HeyGen to consume the ElevenLabs stream instead, a different integration shape than what's wired today. **`[ASSUMPTION]`**: this HeyGen implication is inferred from the fixed OpenAI-only audio/interrupt design, not from a direct re-trace of HeyGen code in this follow-up pass.

### 4.2 Subscriber session flow (client-side parts)

1. **Eligibility pre-flight** (only present on `src/app/sessions/[sessionId]/run/page.tsx:96-107`, not on the course-scoped run page): `GET /api/sessions/{sessionId}/eligibility` returns `{ eligible, issues[] }` with typed issue codes `no_credits | no_subscription | not_published` (lines 15-28). If ineligible, the UI blocks with `EligibilityBlock` and never calls `run/start`. This is a genuine **server round-trip entitlement check**, not a client-side-only gate.
2. `POST /api/sessions/{sessionId}/run/start` (proxied via `src/app/api/sessions/[sessionId]/run/start/route.ts`, called directly from `src/app/sessions/[sessionId]/run/page.tsx:110-116` and from `src/app/subscriber/marketplace/[avatarId]/page.tsx:88-95`). `src/lib/api.ts:1-3` documents that the backend can return **HTTP 402 "Insufficient Credits"**, which the frontend propagates as an `ApiError` rather than pre-computing/blocking on a locally-cached balance — i.e., credit sufficiency is backend-enforced, confirmed by design intent in code, though the actual 402-handling UI call site was not found wired to a user-facing message in the run pages examined (only `ApiError` propagation exists generically).
3. `GET /api/session/ephemeral` fetches a short-lived OpenAI token + avatar render config (`src/lib/sessionService.ts:17-65`); the frontend never holds a long-lived OpenAI key.
4. During the session, each transcript turn is persisted **live, per-turn**, to the backend: `useTranscriptPersistence` (`src/hooks/useTranscriptPersistence.ts:18-51`) POSTs to `/api/sessions/{sessionId}/run/{sessionRunId}/transcript` on every user/assistant turn — this is the one piece of genuine usage telemetry confirmed reaching the backend during a live run.
5. **On session end**, `LearningInterface.handleFeedbackSubmit` (`src/components/learning/LearningInterface.tsx:1140-1171`) computes a `sessionRunMetadata` object including client-computed `session_duration_minutes: Math.round((Date.now() - new Date(classSession.createdAt).getTime()) / 60000)` and user feedback, and calls `onEndSession(sessionRunMetadata)` (line 1159).
   - **Both** call sites that supply `onEndSession` — `src/app/courses/[courseId]/sessions/[sessionId]/run/[runId]/page.tsx:71-73` and `src/app/sessions/[sessionId]/run/page.tsx:165-167` — implement it as `(metadata?: unknown) => { router.push(...) }`, i.e. **the metadata parameter is received and discarded; neither page calls the backend `/stop` endpoint.**
   - `config.api.sessions.runStop` (`src/lib/config.ts:33`) is defined but has **zero call sites** anywhere in `src/` (verified by text search across the repo).
   - The frontend's own proxy routes `src/app/api/sessions/[sessionId]/run/[sessionRunId]/stop/route.ts` and its `.../stop/guest/route.ts` and `.../run/start/guest/route.ts` siblings correctly forward to the backend when invoked, but `route_map()` shows **zero consumers** for all three, and manual text search across `src/` found no fetch call to any `/stop` or `/stop/guest` URL outside these route handlers' own bodies.
   - **Conclusion**: as authored, a session run's end-time, duration, and feedback are computed client-side and then never transmitted — the backend (if it relies on an explicit `/stop` call to close out billing/duration for a run) does not receive one through any path reachable from this repo. `[CROSS-REPO]`: whether the backend derives session end some other way (timeout, last-transcript-turn heuristic) cannot be verified from this repo.

### 4.3 Payment/billing flow (frontend side)

- `src/app/subscriber/billing/page.tsx` and `src/hooks/useBilling.ts` are a **credit ledger UI**: fetch balance (`GET /api/billing/balance`), fetch paginated usage history (`GET /api/billing/usage`), redeem an access code (`POST /api/billing/redeem`). All numeric values (`balance`, `credits_used`, `credits_available`) come from the backend response; the frontend only formats them (`formatCredits()`, `src/app/subscriber/billing/page.tsx:44-46`).
- Access-code issuance (publisher-side "sell seats" mechanism) — `src/lib/avatarApi.ts:221-241` `AccessCodeRecord`/`AccessCodeCreate` (`max_users`, `credits_per_user`, `expires_at`) — is created/edited by the publisher (`src/app/publisher/avatars/[id]/codes/page.tsx`, not read in full but confirmed present in route map) and always round-trips through `bffReq` to `/api/publisher/avatars/{avatarId}/access-codes`. No client-computed price or credit value was found; `credits_per_user` is operator-entered per code, not a fixed frontend constant.
- The subscriber-facing marketplace enrollment button (`src/app/subscriber/marketplace/[avatarId]/page.tsx:66-82`, `handleSubscribe`) shows **no price at all** to the user before calling `subscriptionApi.subscribe(avatarId)` — the only pre-purchase signal shown anywhere is an optional `credits_per_session` stat card on the marketplace list (`src/components/avatars/MarketplaceAvatarCard.tsx:96-104`, sourced from `AvatarPublicResponse.credits_per_session`, a backend-supplied field, not a frontend constant).
- **No Wix code, SDK, webhook handler, or redirect URL exists anywhere in `src/`** (confirmed by full-tree case-insensitive text search; the only two "wix" substring hits in the entire repository are inside `package-lock.json` integrity hashes of unrelated packages, not an actual dependency or reference). This directly contradicts the assumption in the task brief that Wix touchpoints would be visible in this repo — see Open Questions (§7).

## 5. Payments & Billing — Current State vs Target

**Current state, as implemented in this repo:**
- The frontend implements a **credit-balance + access-code-redemption** model end-to-end (`src/app/subscriber/billing/page.tsx`, `src/hooks/useBilling.ts`, `src/lib/avatarApi.ts` `subscriptionApi`/access-code APIs), entirely backed by backend endpoints. No price, tier name, session-limit number, or currency amount is hardcoded in any frontend file found (constants files, `config.ts`, component source were all searched for `price|tier|plan|quota|limit|wix` case-insensitively).
- The one client-side quantity resembling a "limit" is a UI pagination page size (`const LIMIT = 20`, `src/app/subscriber/billing/page.tsx:83`) — purely a display concern, not an entitlement limit.
- Session-length options (`30, 45, 60, 75, 90` minutes) appear as a fixed array in multiple places (`src/app/courses/[courseId]/sessions/[sessionId]/run/[runId]/page.tsx:52`, `src/app/sessions/[sessionId]/run/page.tsx:146`, `src/types/types.ts:114`) — this is a **duration validation/display allow-list**, not a pricing or credit-consumption limit; actual credit consumption is computed and returned by the backend (`credits_used` per usage record).
- Entitlement to start a session is checked via a real backend round-trip (`/api/sessions/{sessionId}/eligibility`, §4.2) and via propagated HTTP 402 on `run/start` — i.e., **entitlement is backend-enforced**, not a bypassable client-only gate, as far as this repo's code paths show.
- Wix: **absent from the frontend entirely.** Either (a) Wix integration lives wholly in the backend/webhooks `[CROSS-REPO]`, (b) purchases happen on an external Wix-hosted site that is not part of either indexed repo and simply results in an access code or backend-provisioned credit balance the subscriber later redeems here, or (c) the "currently via Wix" description in the brief is stale relative to this codebase. This cannot be resolved from the frontend alone — flagged as an open question (§7).

**Target model (cost-plus, 40% margin) — gaps visible from the frontend:**
- Because no price/tier is hardcoded client-side, there is **no frontend blocker** to backend-driven usage-based pricing — the frontend already treats `credits_per_session`, `balance`, and `credits_used` as opaque backend-supplied numbers it merely displays. Moving to metered/usage-based billing would primarily be a backend change; the frontend's billing page and marketplace card would need at most new fields to render (e.g., a live cost-per-minute estimate), not a rewrite of business logic it doesn't currently own.
- The one real gap: the **broken session-stop write path** (§4.2) means any target model that needs an authoritative "session ended at T, ran for N minutes" signal from the client cannot rely on the current `/stop` call chain — it is dead code today. This would need to be fixed (or the backend would need to derive duration independently) before duration-based billing could be trusted end-to-end.
- The disabled "Post-Session Check" feature (§4.1) suggests a partially-built post-session evaluation/billing-adjacent feature that was paused mid-implementation; its eventual activation would need a real backend field, which does not currently exist in `AvatarCreate`/`TeachingPreferences`.

## 8. Recommendations

*(Non-implementation-committing; prioritized; no code changes made or proposed inline.)*

1. **Investigate and fix the session-stop write path first** (§4.2, §6) — this is the one finding that looks like an outright functional bug rather than debt, and it directly affects whether the backend can trust or compute session duration/usage for billing at all.
2. **Delete the confirmed-dead legacy persona subsystem** (`useProfessorPersona.ts`, `src/components/professor/*`, `src/constants/{index,teachingAssistant,examinerPrompt,simpleHandoff}.ts`, `public/prompts/*.txt`) as a low-risk cleanup pass — GitNexus shows zero live references for all of it, but confirm the paired backend routes (`/api/professor/persona*`) aren't independently consumed before removing the frontend proxy handlers.
3. **Remove or clearly quarantine `USE_FRONTEND_EXAMINER_MODE`/`EXAMINER_BASE_PROMPT`** specifically — even though currently dead, its stated intent ("always enforce frontend … regardless of backend prompt state") is precisely the anti-pattern the business should want to avoid re-introducing; deleting it removes the temptation to wire it back in.
4. **Rewrite `README.md`** to reflect the current multi-actor, authenticated, avatar-marketplace architecture — the current file actively misdescribes the system and is a documentation-debt risk for future contributors and for future audits like this one.
5. **Confirm the Wix question with the business/backend team** before any pricing-model redesign work starts, since this repo cannot answer where (or whether) Wix touches the system at all.
6. **Consolidate the session-type domain model** (`ClassSession`/`ClassDetails` vs `SessionDetails`/`SessionRunDetails`) — pick one, since the type explicitly marked "legacy … will be removed" is the one actually in production use, which will confuse the next engineer who trusts the comment.
7. **If/when the "Post-Session Check" feature or usage-based billing display work begins**, prefer server-computed, server-verified duration/usage values over client-computed ones for anything billing-adjacent, given the client-trust issue noted in §6's last row.
8. **Complete or formally shelve the ElevenLabs voice pipeline** (§4.1a, §6) — the backend has already built and bills for the non-OpenAI-provider path; right now that investment is silently unreachable from any live session. If ElevenLabs support is still a business requirement (the brief specifically calls out client demand for customized voices), this needs: an ElevenLabs option in the publisher voice picker, a `voice_provider`-aware branch in the live session components (text-only OpenAI mode + separate synthesis/playback), and a second barge-in mechanism for that separately-played audio — treat this as a scoped design task, not a one-line fix, since it changes the runtime audio architecture, not just a UI dropdown.
